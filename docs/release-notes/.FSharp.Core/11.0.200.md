### Added

* Add the `GeneratedRuntimeAsyncSequenceBase.Close` and `CompleteMoveNext` compiler-services members for runtime-async sequences; `DisposeAsync` now runs pending `finally` blocks through `MoveNextAsync`. ([PR #20655](https://github.com/dotnet/fsharp/pull/20655))

### Fixed

* Correct `FSharpValue.PreComputeTuplePropertyInfo` to report that struct tuples store elements in fields, not properties, and recommend supported tuple readers instead of reporting a valid index as out of range. ([Issue #20801](https://github.com/dotnet/fsharp/issues/20801), [PR #20815](https://github.com/dotnet/fsharp/pull/20815))
* Quotation debug text from `Expr.ToString()`, `Expr.ToString(full)`, and `%A` now prints struct tuple construction as `NewStructTuple`; reference tuples remain `NewTuple`. ([Issue #20800](https://github.com/dotnet/fsharp/issues/20800), [PR #20814](https://github.com/dotnet/fsharp/pull/20814))
* Fix struct tuples in query expressions: selecting one no longer fails with "unreachable", and the items of one that a later operator reads are taken from its fields instead of failing with `ArgumentException: Struct tuples store their elements in fields, not properties`. ([Issue #15522](https://github.com/dotnet/fsharp/issues/15522), [PR #20894](https://github.com/dotnet/fsharp/pull/20894))
* Fix `let` bindings reaching LINQ providers as `Expression.Block`, which no provider translates: in lambdas handed to a provider, records and anonymous records with fields written out of order, tupled lambda parameters, struct copies such as `x.Nullable.HasValue`, and a `let` that only names a member, a sum, difference, product or quotient (by a constant) of members, or is read once now produce plain expressions. A `join` whose key one side builds as a tuple and the other side has ready-made, such as `join p in ps on ((k.KA, k.KB) = p.Pair)`, no longer fails with "Type mismatch when building 'ty'". ([Issue #11131](https://github.com/dotnet/fsharp/issues/11131), [Issue #15648](https://github.com/dotnet/fsharp/issues/15648), [Issue #11332](https://github.com/dotnet/fsharp/issues/11332), [Issue #3782](https://github.com/dotnet/fsharp/issues/3782) for records with fields out of order, [PR #20895](https://github.com/dotnet/fsharp/pull/20895))
* Fix a lambda nested in another lambda that goes to a LINQ provider, such as `db.Orders.Any(fun o -> o.CustomerId = c.Id)` inside a query `where`: when it reads a parameter of the outer lambda, it becomes a quoted lambda, as in C#, instead of a run-time call to `QuotationToLambdaExpression` that no provider can translate. ([Issue #2758](https://github.com/dotnet/fsharp/issues/2758), [PR #20896](https://github.com/dotnet/fsharp/pull/20896))
* Fix LINQ providers failing on queries composed over a tuple or record projection (for example the tuples of a nested query taken apart by the next `for`, or a record read by a later `Where`): tuple, struct tuple, record and anonymous record constructions now name the member each argument becomes, as C# anonymous types do. ([Issue #15133](https://github.com/dotnet/fsharp/issues/15133), [Issue #40](https://github.com/dotnet/fsharp/issues/40), [PR #20897](https://github.com/dotnet/fsharp/pull/20897))
* Fix `distinct` after a member of a tuple or record that an earlier operator selected: `for (city, _) in (select (b.Address.City, b.Id)) do select city; distinct` returned a city once for each id, because the provider applied `DISTINCT` to both columns of the earlier projection, and now returns each city once. ([PR #20897](https://github.com/dotnet/fsharp/pull/20897))
* Fix a query that selects a tuple or record holding a nested query over a sequence that ends in a sort, such as `select (x, query { for y in ys do sortBy y })`: it no longer fails with "Type mismatch when building 'args'". ([PR #20898](https://github.com/dotnet/fsharp/pull/20898))
* Fix LINQ providers failing on a `groupBy` or `groupValBy` over tuples or records followed by `select (g.Key, g.Count())`, `g.Sum(..)`, `g.Average(..)` and similar: FSharp.Core no longer rebuilds each group as a `Grouping` of tuples in the middle of the query, and no longer re-projects every element after a `join` or a `for`. ([Issue #47](https://github.com/dotnet/fsharp/issues/47), [PR #20899](https://github.com/dotnet/fsharp/pull/20899))
* Fix a `find` in a nested query over elements that the translation rebuilds, such as `select (c.Name, query { for o in c.Orders do for o2 in c.Orders do find (o.Id < o2.Id) })`: it no longer fails with "Type mismatch when building 'args'". ([PR #20899](https://github.com/dotnet/fsharp/pull/20899))
* Fix LINQ providers failing on F# functions in queries and in lambdas passed as `Expression<Func<..>>`: `fst`, `snd`, `isNull`, `box` and the math functions (`abs`, `sqrt`, `floor`, `ceil`, `round`, `truncate`, `sign`, `exp`, `log`, `log10`, the trigonometric functions, `min`, `max`, `**`) on primitive types now become the tuple reads, null comparisons, conversions and `System.Math` calls a C# lambda has, instead of calls into FSharp.Core. ([PR #20900](https://github.com/dotnet/fsharp/pull/20900))
* Fix LINQ providers failing on, or evaluating on the client, queries that end by consuming the tuples or records a query produces: `exists`, `all`, `sumBy`, `averageBy`, `minBy`, `maxBy` and `count` after two `for`s, a `join` or a tuple or record `select` now work on the query's own elements instead of on tuples and records rebuilt at the end of the query. ([PR #20901](https://github.com/dotnet/fsharp/pull/20901))

### Changed

* A query that ends by selecting a tuple or record now gives the LINQ provider a single `Select` building it, as C# does, instead of a `Select` of an internal `AnonymousObject` followed by a second `Select` converting it. ([PR #20898](https://github.com/dotnet/fsharp/pull/20898))
